# 部署与开发

直接拉取镜像与源码构建的启动步骤见 [README](../README.md#启动)。以下介绍路径、运行用户、开发与版本发布配置。

## Docker 配置

从项目根目录复制 `.env.example` 为 `.env`，按宿主机环境修改配置。默认容器用户为 `1000:1000`；容器启动不会改变宿主机目录所有权。

| 配置 | 用途 |
| --- | --- |
| `PORT` | Web 访问端口，默认 8080 |
| `BIND_ADDRESS` | 宿主机监听地址，默认 `0.0.0.0`；本地验证脚本使用 `127.0.0.1` |
| `PUID` / `PGID` | 容器运行用户与用户组 |
| `DATA_PATH` | 数据库、设置、Cookie 和头像目录 |
| `DOWNLOAD_PATH` | 下载文件目录 |
| `ARCHIVE_PATH` | 归档目录 |
| `LOG_PATH` | 任务日志目录 |
| `TZ` | 时区，默认 `Asia/Singapore` |
| `GALLERY_DL_VERSION` / `YTDLP_VERSION` / `FFMPEG_VERSION` | 本地构建的引擎版本覆盖，留空使用发布清单 |

```sh
cp .env.example .env
mkdir -p data logs downloads archive
# Linux 上按 .env 中的 PUID/PGID 设置目录所有者。
sudo chown -R 1000:1000 data logs downloads archive
docker compose up -d --build
```

容器目录分别为 `/data`、`/downloads`、`/archive`、`/logs`。数据库保存在 `/data/media.db`，Cookie 保存在 `/data/cookies`，任务日志保存在 `/logs/<created-at>-<task-id>.log`。

归档需要挂载且可写的目录。不使用归档时，可删除 Compose 的 `/archive` 挂载行。目录不可用时，已完成内容等待恢复，历史中提供归档重试。跨文件系统归档在复制成功后移除源文件。

不挂载目录也可以下载，但删除容器会丢失容器内的数据，且无法启用归档。自定义运行用户时，运行目录需允许该用户写入。

```sh
docker compose logs -f
docker compose down
```

## 设置与初始化

新数据库从 `internal/config/initial-settings.json` 读取默认设置；修改后重新构建，只对首次初始化生效。已有数据库使用界面保存的设置。`YTDLP_MAX_CONCURRENT` 和 `GALLERY_DL_MAX_CONCURRENT` 可覆盖初始化并发，使用示例 `.env` 时分别为 2、10。新任务默认自动归档在首次初始化时按归档目录挂载状态设置：已挂载则开启，未挂载则关闭。界面在未挂载时禁用该选项并取消勾选。

程序使用当前数据库结构。涉及结构变化的版本更新需手动重建数据库；启动时保留已有数据库。

## 引擎配置

实际下载由 gallery-dl、yt-dlp 和 FFmpeg 执行。系统设置中可查看引擎版本、编辑 gallery-dl JSON 配置。构建固定版本由 `internal/config/release.json` 管理，启动时使用镜像内已安装的版本。

Instagram 目录名称解析直接请求帖子 HTML，从作者字段或主页链接提取账号。名称解析不发送 Cookie；扫描与下载自动使用已保存的 Cookie。名称解析与引擎请求共用桌面 Chrome User-Agent、中文 Accept-Language 和 Instagram Referer，可用 `INSTAGRAM_USER_AGENT` 覆盖 User-Agent。

## 本地开发与验证

功能修改后统一通过 Docker 镜像验证。本地需要 Docker，镜像构建负责安装 Go、Node、Python 与下载引擎。

```sh
sh scripts/local-deploy.sh
docker compose logs -f media-harbor
```

脚本重新构建 `media-harbor:local` 并重建容器，访问地址为 `http://127.0.0.1:8080`。默认使用项目内 `data`、`downloads`、`archive` 和 `logs`，已有数据库与文件保留；目录可通过 `.env` 的挂载配置覆盖。容器默认使用宿主机当前用户的 UID/GID，也可显式设置 `PUID`、`PGID`。首次切换到 Docker 前先停止占用 8080 的原生服务。单元测试与类型检查作为构建前检查，最终验收以新镜像中的版本、API 和界面行为为准，不通过替换容器内文件更新。

测试期间在“系统设置 → 调试”开启总开关，条目限制默认 10，支持输入自定义正整数；保存后扫描、调度和任务级重试使用该上限。关闭总开关并保存恢复完整处理，范围外记录保留。默认关闭，关闭状态重新打开设置时条目输入恢复为 10；已保存的开启状态与限制无需重启即可生效，已运行任务使用启动时的设置。轮播中的每张照片或视频分别计为一个条目。

任务管理每个任务配置只显示一行，显示扫描状态与下载统计，并提供统一日志、取消和重试。取消会停止该订阅所有尚未结束的任务；重试受测试上限约束。日志含时间、阶段、账号识别、媒体 ID、发布日期、地址、新增/重复数量、耗时和失败原因，扫描等待时每 5 秒记录进度。

YouTube 每个并发名额对应一个视频及其附属任务。主视频完成或复用已有文件后，依次处理已开启的评论与元数据、字幕、缩略图、额外音频及本地音频提取；全部附属阶段结束后才释放名额并启动下一条视频。附属阶段失败会记录错误并继续处理其余附属项，父任务最终报告失败；主视频失败则不启动附属阶段。各下载阶段复用本次解析清单，媒体请求 403 时重新解析地址并最多再尝试一次。

系统设置中的语言同时传给 YouTube 扫描、下载和请求验证，使用平台提供的本地化标题命名新文件。下载历史以实际下载元数据中的标题为准；平台未提供对应语言标题时保留原始标题。语言变更不批量重命名已有文件。

每个视频只下载一份符合语言配置的字幕，按配置顺序选取，例如 `zh.*,en` 优先中文，再回退英文。同一语言组优先人工字幕，其次原始自动字幕，最后自动翻译；已有符合条件的字幕不重复下载。容器安装 `yt-dlp[default,curl-cffi]`，提供引擎所需的浏览器请求模拟能力。

macOS 不读取 Linux mountinfo，挂载状态显示“未知”，归档不可启用；使用 Docker 验证挂载归档流程。默认容器时区是 Asia/Singapore，Cron 跟随进程时区，可修改 `TZ`。

```sh
go test -race ./...
node --test web/tests/*.test.mjs
# 已安装固定版本引擎时，验证本地视频的下载与音频产物：
PATH="$PWD/.venv/bin:$PATH" RUN_ENGINE_INTEGRATION=1 go test ./internal/engine -run TestCLIIntegration -v
# 镜像构建后，验证容器目录、真实引擎流程和持久化：
SMOKE_IMAGE=media-harbor:local python3 scripts/container-smoke.py
cd web && npm run build
```

单元及业务集成测试使用可控引擎验证扫描、去重、下载文件归位、并发、取消、重启恢复及归档，不代表真实 Instagram/YouTube 访问验收。平台能否下载取决于网络、Cookie 和上游引擎能力。

容器验证使用 `SMOKE_TIMEOUT` 设置每阶段等待预算，默认 30 秒。GitHub 工作流的 arm64 模拟验证使用 180 秒。脚本输出启动、扫描、下载归档、增量和重启各阶段耗时；任务失败立即终止，超时保留最后状态，失败时同时输出服务日志、任务状态、内容状态及独立下载日志。

## 镜像发布与版本管理

工作流 [`Build and publish Media Harbor`](../.github/workflows/release.yml) 使用仓库自带的 `GITHUB_TOKEN` 发布到 `ghcr.io/<owner>/media-harbor`，不需要额外配置注册表密码。`main` 提交执行后端测试、前端测试与构建，以及 amd64/arm64 容器验证，通过后发布 `sha-<commit>` 并更新 `latest`；PR 只执行验证。日常提交不自动递增版本号，也不覆盖已有版本镜像。推送 `v1.0.0` 等正式版本标签时生成版本镜像、`sha-<commit>` 和 `latest`；带 `-` 的预发布标签不更新 `latest`，手动运行只生成 `sha-<commit>`。容器验证使用本地生成素材，覆盖 UID/GID、目录挂载、日志目录、下载与音频产物、归档、重启持久化和只读下载目录；不访问真实媒体平台。

每 12 小时（UTC 00:17、12:17，北京/新加坡时间 08:17、20:17）检查 PyPI 的 gallery-dl、yt-dlp 稳定版本，以及 Alpine 3.23 两个架构都可安装的 FFmpeg。没有更新时跳过构建；有更新时更新 `internal/config/release.json` 中对应依赖，并只递增 `version` 的第三位，例如 `1.0.99 → 1.0.100`，多个依赖更新合并为一次发布，前两位由项目控制。

自动流程先将清单提交与 `v<version>` 标签原子推送到远端，再对同一个提交执行测试、amd64/arm64 容器验证和一次镜像发布，生成版本镜像、`sha-<commit>` 与 `latest`。推送使用仓库自带的 `GITHUB_TOKEN`，不会再次触发提交或 tag 的 `push` 工作流，不需要额外配置 Token。构建失败时提交和 tag 已保存，但不会发布镜像，可在 Actions 中重新运行该次失败任务。手动勾选 `check_updates` 可立即检查。仓库需允许 Actions 写入代码，分支保护规则需允许机器人提交。

当前远程仓库为 `leapsea/media-harbor`，对应镜像地址为 `ghcr.io/leapsea/media-harbor`。首次发布后，如需匿名拉取，在 Packages 中将镜像可见性设为 Public。

版本号保存在 `internal/config/release.json`。发布时先修改其中的 `version` 并提交代码，再运行 `scripts/tag.sh`。脚本读取版本号、创建对应的 `v` 标签并推送至 `origin`，触发镜像构建。例如将版本改为 `1.1.0` 后：

```sh
git add internal/config/release.json
git commit -m "Release v1.1.0"
git push origin main
sh scripts/tag.sh
```

手动运行可指定 gallery-dl、yt-dlp、FFmpeg 的版本。FFmpeg 使用 Alpine 包版本，独立于 Python 包。固定镜像标签或 digest 部署，回滚时改回已有镜像引用：

```sh
# .env: IMAGE=ghcr.io/<owner>/media-harbor:v1.0.0
docker compose pull
docker compose up -d --no-build
```
